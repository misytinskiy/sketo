# Доступ в кабинет

Вход: `/login`. Самостоятельной регистрации нет. Supabase Auth проверяет email и пароль;
сервер читает активное членство из `staff_members` при каждом запросе. Все серверные
действия каталога проверяют доступ самостоятельно, независимо от layout и proxy.
Предпросмотр также доступен только вошедшим сотрудникам.

Роли интерфейса:
- **Админ** — каталог и `/staff/users`: добавление и удаление пользователей.
- **Персонал** — все существующие операции каталога, включая публикацию и удаление товаров.

Используется существующая схема: `admin` → Админ, `editor` → Персонал.
Старой роли `viewer` доступ не предоставляется. Миграция и перенос каталога не нужны.
Роль никогда не берётся из пользовательских metadata, формы или cookie.

## Настройка

Нужны `DATABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`. Секрет service role хранится только на сервере.
В Supabase должен быть включён вход по email/password. Публичную регистрацию
рекомендуется выключить в Auth; даже зарегистрированный через API пользователь без
активной записи `staff_members` не получает доступ к кабинету. Лимиты попыток входа
настраиваются в Supabase Auth.

Первый администратор создаётся только операторской командой:

```sh
npx tsx scripts/bootstrap-admin.ts --email admin@example.com --credentials-file /private/tmp/sketo-first-admin.txt
```

Если email уже есть в Auth и подтверждён, пароль сохраняется. Для нового аккаунта
генерируется случайный пароль и записывается в новый файл с правами `0600`, без
вывода пароля в журнал. Передайте пароль владельцу и удалите файл после сохранения
в менеджере паролей. Команда откажет, если уже есть другой активный администратор.
Она не отправляет писем.

Остальных пользователей администратор добавляет через `/staff/users`, указывая имя,
email, роль и пароль от 12 символов. Пароль не возвращается клиенту и не записывается
в аудит. Добавление не меняет пароль существующего аккаунта: занятый email отклоняется.

## Удаление и восстановление после сбоя

Самоудаление и удаление последнего администратора запрещены. Сначала транзакционно
отзывается членство, затем удаляется аккаунт Auth и запись сотрудника. При сбое
остаётся отключённая запись с возможностью повторить удаление. Новые запросы с
прежней сессией уже не авторизуются; начатая ранее операция может завершиться.
Создание/отзыв/удаление сотрудников пишутся в аудит без паролей.

## Восстановление и смена пароля

- `/login/forgot-password` отправляет стандартное письмо Supabase Auth. Ответ не
  сообщает, зарегистрирован ли адрес.
- `/auth/recovery` обменивает одноразовый PKCE-код на сессию. Открывайте письмо
  в том же браузере, где отправлен запрос: там хранится PKCE verifier.
- `/login/reset-password` доступен для смены пароля только после успешного
  recovery-обмена и с активным членством сотрудника. Подписанное HttpOnly-разрешение
  действует 15 минут и удаляется после успешной смены пароля.
- `/staff/security` позволяет сменить пароль с проверкой текущего пароля.
  Новый пароль: 12–256 символов, с повторным вводом для подтверждения.

Перед использованием писем на рабочем сайте:

1. Задайте `SITE_URL=https://ваш-домен` в окружении приложения.
2. В Supabase → Authentication → URL Configuration задайте Site URL и добавьте
   точный адрес `https://ваш-домен/auth/recovery` в Redirect URLs. Для разработки
   отдельно добавьте `http://localhost:3000/auth/recovery`.
3. Настройте SMTP для отправки писем сотрудникам и проверьте адрес отправителя.
4. Шаблон Reset Password должен использовать стандартную ссылку
   `{{ .ConfirmationURL }}`. Если он был изменён на собственный token_hash-маршрут,
   верните эту ссылку для используемого здесь PKCE-сценария.
5. Проверьте доставку на тестовый адрес сотрудника, повторное использование ссылки,
   истёкшую ссылку и вход с новым паролем. Пароль реального администратора при
   проверке не меняйте.

Источник: https://supabase.com/docs/guides/auth/passwords

## Автоматические проверки

```sh
node --test tests/*.test.mjs
npx tsc --noEmit
npm run lint
```

Перед развёртыванием проверить на тестовом Supabase: вход обеими ролями,
перезагрузку после истечения access token, отказ гостям и персоналу в управлении
пользователями, отзыв доступа с открытой сессией, повтор удаления при сбое Auth.
