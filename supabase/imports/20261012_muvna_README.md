# MUVNA: отдельный каталог аксессуаров

Подготовлено по `Muvna.pdf`: 161 SKU → 110 карточек / 161 вариант.
После уточнений заказчика от 13 октября включены все позиции прайса. Дополнительные проверки перед публикацией сохранены в [списке уточнений](20261012_muvna_unresolved.md).
Все товары — MUVNA. Оптовые цены не сохраняются. Одинаковые цвета объединяются только у одной модели, размера, комплектации и розничной цены; разные цены остаются отдельными карточками.

## Запуск

Сначала проверить [карточки и группировку](20261012_muvna_catalog.md), сохранить резервную копию БД и проверить на тестовом проекте Supabase.
В SQL Editor существующего проекта Sketo выполнить по порядку:

1. [Миграцию структуры](../migrations/20261012010000_accessories_catalog.sql).
2. [Импорт товаров](20261012_muvna_catalog.sql).

Миграция использует существующие `locale`, `editorial_state`, `editorial_role`, `staff_members` и `update_updated_at()`. Полный bootstrap повторно запускать в рабочей БД не нужно.
Импорт транзакционный: конфликт существующего slug/SKU останавливает загрузку без перезаписи данных. Повторный запуск того же импорта ничего не меняет, включая отредактированные цены и остатки. Для исправлений после загрузки нужна отдельная миграция, не удаление записи о выполненном импорте.

Основной импорт дополнен всеми 30 первоначально исключёнными артикулами по ответам заказчика. Если прежняя версия на 131 или 142 варианта уже выполнена, новая версия основного файла намеренно остановится из-за изменившегося содержимого: для такой базы нужен отдельный добавочный импорт. Не удалять ранее загруженные данные или историю импорта для обхода защиты.
DC2397 объединён с DR2271/DR2274, SP2679 — с SP2680/SP2681. Совместимость BP2554/BP2555 не указывается. Размер `58/58.35mm` сохранён текстом из прайса, без создания вымышленных отдельных вариантов диаметра. Подтверждения заказчика записаны в файле источников.
Термосы разделены на 615/685 мл, термокружки — на 260/450 мл; внутри каждого объёма объединены цвета с одинаковой ценой. Plan B — отдельная карточка: Plan A плюс портативная электрическая кофемолка, без предположения о её модели. ES2625 — вишнёвое дерево по подтверждению заказчика, несмотря на walnut в адресе ссылки. Три присланные ссылки не открылись при проверке; сведения внесены по ответам заказчика, дополнительные характеристики по названиям URL не выдумывались.

Все карточки создаются как `draft`, описания — на русском. Переводы EN/KZ ещё не подготовлены.
Валютой принята **KZT**, но PDF её явно не указывает: подтвердить перед публикацией. Цены перенесены буквально из розничной колонки; `price_verified=false`.
Остатки сохранены только как недатированный снимок прайса: `inventory_verified=false`, `stock_recorded_at=NULL`. Это не актуальный склад и не резервирование.

## Структура

- `accessory_products`: карточка, бренд, категория, характеристики и статус публикации.
- `accessory_translations`: локализованные название и описание.
- `accessory_variants`: цвет, SKU, розничная цена и остаток.
- `accessory_images`: общие фотографии либо фотографии конкретного варианта.
- `accessory_import_batches` / `accessory_import_rows`: служебная история импорта и соответствие строкам PDF.

Таблица `products` и оборудование с `equipment_type=accessory` не изменяются.
В staff подключены таб аксессуаров и редактор `/staff/accessories/edit/[id]`: переводы RU/EN/KZ, характеристики, варианты, цены/остатки, статусы и фотографии с привязкой к цвету. Публичная витрина: `/accessories`, карточка: `/accessories/[slug]`; ссылка в основной навигации добавлена только в футер. На витрину попадают опубликованные карточки с активными вариантами; неподтверждённые цены и количество остатков публично не выводятся. Новые таблицы пока читаются и изменяются параметризованными SQL-запросами; не применять `drizzle-kit push` для синхронизации этой структуры до обновления Drizzle-модели.
Сохранение проверяет права сотрудника и версию карточки, выполняется транзакционно и записывает прежние значения в `audit_logs` с `catalog=accessories`. Изображения загружаются в `catalog/accessories/<product-id>/`; снятие фото с карточки не удаляет файл из Storage. Незавершённые загрузки фиксируются в журнале, автоматическая очистка таких файлов ещё не подключена. Для редактора не нужна дополнительная миграция поверх структуры аксессуаров и существующего bootstrap.
Публичный доступ разрешён только к опубликованным карточкам, активным вариантам и одобренным фото. Черновики и происхождение данных доступны сотрудникам согласно существующим ролям.
Для новых таблиц добавлена изолированная функция `accessory_staff_access`: в версии `is_staff_member` из bootstrap имя переменной `current_role` конфликтует с SQL `CURRENT_ROLE`. Тест воспроизвёл отказ доступа даже сотруднику. Существующая функция и права других каталогов не изменяются; состояние этой функции в рабочей БД нужно проверить отдельно.

## Фото и выбор цвета

Рекомендованная схема: палитра выбирает конкретный SKU, а галерея показывает его фотографии плюс общие фотографии товара.
`accessory_images.variant_id` указывает вариант; `NULL` — фото для всех цветов. База запрещает привязать вариант к фото другого товара.

[Исследованные источники](20261012_muvna_sources.json) содержат ссылки на карточки и кандидаты изображений с привязкой к SKU. Проверены каталоги MUVNA global, MUVNA Australia, MUVNA Russia и дополнительные карточки, указанные в файле. Совпадение SKU не гарантирует правильность фотографии: в источниках встречаются противоречия по цветам.
Изображения **не загружены в хранилище и не импортированы как готовые фото**. Нужно сверить цвет/модель, право использования, загрузить одобренные файлы в своё хранилище и записать URL с `is_approved=true`. Цветовые HEX-коды намеренно не выдуманы.
Не добавлять по источникам неподтверждённые размеры, совместимость, гарантию или комплектацию. Отдельные уточнения к распознанным товарам также перечислены в документе с вопросами.

## Воспроизводимость и проверка

- `extract_muvna.py` извлекает исходные строки (нужен PyMuPDF), исключая оптовую колонку. SHA-256 PDF сохранён в `20261012_muvna_source.json`.
- `python3 supabase/imports/build_muvna_import.py` пересобирает каталог, SQL и документы из сохранённых исходных строк и вручную проверенных групп; БД и сеть не использует.
- Необязательные исследовательские кэши `/tmp/muvna-{global-1,au-1,au-2,au-3}.json` нужны только для пересборки файла источников. Без них существующий файл источников сохраняется.
- `validate_muvna.sql` предназначен только для одноразовой тестовой БД после bootstrap/миграции/импорта. Проверяет количества, одинаковую цену внутри группы, RLS, роли и привязку изображений. Тестовые изменения откатываются.

Для будущего низа страницы аксессуара выбран вариант №3: универсальное оформление, без необходимости готовить отдельное декоративное фото каждого товара. Его реализация не входит в этот импорт.
